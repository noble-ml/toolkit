Training

model.train(train, validation=val, epochs=100)
model.train(train, validation=val, epochs=100, device="cuda")

train and validation are Felix splits (dataset.train, dataset.val). A whole Felix dataset also works: its own splits are used.

Returns the history: one dict per epoch (epoch, loss, box, obj, cls, lr, seconds, and with validation val_loss, val_box, val_obj, val_cls, map50, map50_95, precision, recall, f1, fitness). It is also kept in model.history.

Progress

Training shows a live panel. In a terminal it redraws in place; in a notebook (Jupyter, VS Code, Colab) it redraws in the cell's output, about twice a second. quiet=True hides it.

  • The bar: epoch and step, and the running *training* loss of the current epoch with its parts (box, obj, cls) and the learning rate.
  • After each epoch, a line is added to a table under the bar:
epoch   train loss   val loss   mAP50   mAP50-95
    1        7.963     14.018   0.000      0.000
    2        3.718     14.239   0.000      0.000
    3        3.099     13.865   0.000      0.000
    4        2.664      9.462   0.017      0.011
    5        2.497      4.697   0.585      0.191  ← best

The validation loss is the same loss as training (box + confidence + class), measured on the validation pictures with the weights that get saved (the moving average, when ema=True). Early on it is often higher than the training loss, because that average lags behind the newest weights; it catches up as training settles. The table shows the latest 15 epochs (continued runs include the earlier ones); every epoch is in model.history, e.g.:

for r in model.history:
    print(r["epoch"], r["loss"], r["val_loss"], r["map50_95"])

Defaults

  • Weights: convolutions uniform in ±1/√fan_in; BatchNorm γ=1, β=0; the head starts with box distances of about 1.3 strides and confidences of about 1%, which keeps the first steps stable.
  • Optimizer: AdamW, weight decay 5e-4 on weights (not on biases and BatchNorm).
  • Schedule: linear warm-up (about 3 epochs, at least 100 steps), then cosine decay to 1% of lr.

Learning rate

Two things adapt, one doesn't:

  • Per weight (adaptive): AdamW gives every weight its own effective step size, from the running size of its gradients. Weights with big, noisy gradients take smaller steps; quiet ones take bigger steps.
  • Over time (scheduled): the overall lr follows a fixed plan worked out from epochs: it ramps up from almost 0 during warm-up, then glides down along a cosine curve to 1% of lr at the last epoch. The lr on the progress bar is this value.
  • Not adaptive: it doesn't react to the validation loss (no "reduce on plateau"). Because the plan depends on epochs, a run with more epochs decays more slowly; a continued run keeps following the plan for the new total.
  • Stability: gradients clipped at norm 10; a NaN/inf loss stops training with an explanation.
  • Best model: highest 0.1 × mAP50 + 0.9 × mAP50-95 on the validation data (lowest loss without validation).

Crash protection

  • Ctrl+C, kill, closing a service (SIGTERM): training finishes the step it is on (a few seconds), saves output/last.nbm with the exact position (epoch *and* step), and model.train returns the history so far. A second Ctrl+C stops at once.
  • Autosave: inside an epoch, last.nbm is also saved every autosave minutes (default 10). A power cut, an out-of-memory kill or a crashed machine loses at most those minutes, not the epoch (an epoch at 640 px on a laptop CPU can take over an hour).
  • Errors: if anything else goes wrong (a broken image, a full disk, ...), progress up to the last finished step is saved before the error is shown. A NaN / infinite loss is the exception: those weights are broken, so the last good save is kept.
  • Safe files: checkpoints are written to a temporary file, flushed to disk and then renamed over the old one, so a crash during a save leaves the previous checkpoint, never half a file.

To continue, load last.nbm and train again with the same arguments:

model = wf.load("runs/train/last.nbm")
model.train(train, validation=val, epochs=100)     # "continuing epoch 7 from step 412 of 996"

It resumes at the same step, with the same shuffled order for that epoch, the same optimizer state, EMA, and BatchNorm statistics; without augmentation the result is the same as a run that never stopped.

Memory

Each training step keeps every layer's output until the backward pass has used it, so memory grows with batch size, picture size and model width. On CPU (Linux), training first measures what one step needs (a forward and backward pass on one blank picture, taking a moment) and compares it with free RAM:

  • It fits: normal training.
  • It fits only with low-memory mode: it is switched on and a note says so. Each Conv → BatchNorm → activation unit and each block keeps only its input; its insides are recomputed during backward. Same numbers (gradients and BatchNorm statistics match normal training), about 30% slower, about 40% less memory.
  • It doesn't fit at all: training stops before it starts, with the largest batch_size that fits, instead of the system killing it an hour in.

Pass low_memory=True to force it on any device, or False to turn the check off. Datasets are read from disk as needed, so their size doesn't matter; only the batch does.

Sharded datasets

A folder of .sh_felix shards (fx.shard, felix shard, fx.export("name.sh_felix")) trains one shard at a time: the shard in use is read into memory in one pass, the next one loads in the background while it trains, and each is dropped after its last batch, so at most two shards are in memory and reads from disk (or a network drive) are long and sequential. Shuffling keeps that true: every epoch visits the shards in a new random order and shuffles the pictures inside each shard (with many small shards that is close to a full shuffle). The order comes from the run's seed, so crash protection still resumes at the exact step. The memory check counts the two shards.

model.train("voc_shards/", epochs=100)          # a path, or fx.load("voc_shards/") and its splits

Fine-tuning

model = wf.fine_tune("runs/base/best.nbm", new_data, epochs=30, freeze="backbone")   # a path or a loaded model
  • wf.fine_tune(model, data, validation=None, epochs=30, *, lr=3e-4, freeze=None, output="runs/fine_tune", **train_options) starts a new run from the model's weights and returns the model: a fresh optimizer, learning-rate schedule and epoch count (epochs counts the fine-tuning epochs; the history starts again).
  • Other classes: if the dataset's classes differ from the model's, the head's last prediction layer is rebuilt for them (every other weight is kept) and the model takes the new class names. model.set_classes(names) does the same by hand.
  • freeze=N keeps the first N layers after wf.input fixed; freeze="backbone" keeps everything before the first FPN / PAN / head. Frozen layers do not change, use their stored BatchNorm statistics, and need no gradient (faster). They are released when training ends.
  • Any model.train option can be passed (batch_size, device, img_size, augment, …). The default lr is 3e-4; with a frozen backbone 1e-3 is fine.

Measured on a small new dataset (46 training pictures of two shapes a base model never saw, 60 epochs, CPU, a few seconds each): from scratch mAP50 0.005; fine-tuned with a frozen backbone 0.916; fine-tuned with every layer 0.894 (best 0.926).

Continuing

model = wf.load("runs/train/last.nbm")
model.train(train, validation=val, epochs=150)

epochs is the total target: a run saved at epoch 80 continues from 81 to 150, with the optimizer state, raw weights, EMA and history restored. A model already at the target does nothing (and says so). If the saved optimizer state doesn't fit the model, a fresh optimizer is created with a note.

Speed

Measured on the demo detector (1.3M parameters, 256×256, batch 16): about 47 images/s on a GTX 1050. The workflow init model at 640×640, batch 16, on an Apple M2 GPU (device="mps"): about 45 images/s (0.3.7; 16 before).

On CPU (0.4), the workflow init model on a 2012 laptop (Intel i5-3210M, 2 cores, AVX, 4 GB RAM):

0.30.4
320×320, batch 163.5 images/s11.7 images/s
one epoch, 642 pictures at 320, with validation182 s52 s
640×640, batch 160.76 images/s (2.8 GB)3.0 images/s (1.8 GB)

What changed: convolutions use a packed, register-blocked matrix multiply (the BLIS design) that reads the picture directly instead of building a 9× larger copy first; BatchNorm and the activation run as one vectorised pass; and backward frees each layer's saved values as soon as they are used. All of it is plain fp32 with the same results.

The cost of a step grows with the picture area: 640×640 is 2.4× the work of 416×416 and 4× of 320×320. If your objects aren't tiny, a smaller img_size is the biggest speed-up there is. Workflow's kernels are its own; they are slower than cuDNN-backed frameworks on large models, which is the price of owning the stack.
