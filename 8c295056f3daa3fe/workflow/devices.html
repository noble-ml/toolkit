Devices and backends

Workflow computes with its own engine. PyTorch is not used.

DeviceBackendStatus
"cpu"native C core: packed, register-blocked GEMM convolution (AVX / AVX2+FMA / NEON, no im2col copy), depthwise kernels, a thread pool, fused BatchNorm / activation kernelsstable
"cuda", "cuda:N"Workflow's own CUDA kernels (implicit-GEMM convolution, parallel BatchNorm reductions, fused BatchNorm + activation, pooling, ...), shipped as PTX and run through the NVIDIA driverstable
"gpu"CUDA if present, else the Apple GPU
"mps"Apple GPU through MLX, Apple's open-source Metal array library (pip install mlx)experimental: warns when used
"auto"CUDA, then CPU (experimental MPS is never picked implicitly)
"modal", "modal:GPU", wf.Modal(...)training only: the same training on a Modal cloud GPU (or Modal CPU cores), see belowstable
model.device("cuda")                           # or model.train(..., device="cuda")
workflow devices                               # what this machine has, and why something is unavailable

A requested device that isn't available raises a DeviceError explaining why (no driver, no MLX, no GPU) and what to do. Workflow never silently runs on another device than the one you asked for.

Choosing the device once: wf.use

wf.use("cuda")                                  # train and predict on CUDA
wf.use("modal:a100")                            # train on Modal; predict / evaluate here ("auto")
wf.use(train="modal:h100", run="mps")
with wf.use("cpu"): ...                         # only inside the block
wf.use()                                        # the current choice and where it comes from
wf.use(None)                                    # back to the defaults

Two settings: train (model.train, wf.fine_tune) and run (predict, evaluate, inference). wf.use(device) sets both, except a Modal device, which sets only train. First match wins:

  1. the call's own device= argument
  2. the model's device: model.device(...), or a device= passed to an earlier call on that model
  3. wf.use(...)
  4. the environment: WORKFLOW_TRAIN_DEVICE (training), WORKFLOW_DEVICE (both; a Modal value only for training)
  5. "auto"

wf.use checks the device straight away (an unavailable one raises DeviceError then), and the training panel shows where a device came from when it wasn't the call's own (cpu (from wf.use)). Felix has the same for its models: fx.use("cuda").

Modal (cloud GPUs)

model.train and wf.fine_tune can run on Modal's GPUs, so a Mac or a laptop can train on an H100. It's the same training code, on cuda with Workflow's own kernels, in fp32.

model.train(data, epochs=100, device="modal")                  # L4
model.train(data, epochs=100, device="modal:H100")
model.train(data, epochs=100, device=wf.Modal(gpu="A100", hours=12, volume="workflow"))
model.train(data, epochs=100, device=wf.Modal(gpu="cpu", cpus=16))
wf.Modal.pull("20261123-120222-828431", output="runs/train")   # a run whose connection dropped
  • Setup: pip install modal (or pip install workflow[modal]), then modal token new once. GPU functions need a payment method on your Modal account; Modal bills the time to it.
  • GPUs: T4, L4 (default), A10G, L40S, A100, A100-80GB, H100, H200, B200; "cpu" uses cpus Modal CPU cores.
  • Data (automatic): the dataset (a Felix folder, .felix file or shard folder, a split of one, or its path) goes up once to the Modal Volume workflow under datasets/NAME-FINGERPRINT. Later runs reuse it while its files are unchanged. Splits are sent as their list of images, so data.train / data.val train on exactly the same pictures. On the remote machine the dataset is copied to its local disk before training, so epochs read it at disk speed instead of over the network (it is read from the Volume directly if the disk is too small).
  • CPU next to the GPU: cpus cores (default 8) are reserved to decode and letterbox pictures while the GPU trains.
  • Code: the container runs the locally installed workflow (and felix) packages, so the remote code is exactly your version. Python matches your local version.
  • Checkpoints: written to the Volume under runs/RUN as training goes (autosave included), then copied into output. After the run the local model holds the trained weights and training state, as after a local run. Ctrl+C, an error or the time limit (hours, at most 24) still bring back last.nbm; training it again continues there.

How the Apple GPU backend is fast

  • Tensors live on the GPU channels-last (MLX's own layout), so convolutions never reshuffle memory.
  • A training step is built as one graph and sent to the GPU at once, instead of waiting after every operation.
  • Custom Metal kernels for BatchNorm statistics (one read of the data instead of several) and max pooling (the gradient goes straight to the winning pixel).
  • BatchNorm followed by an activation (BatchNorm2D() then SiLU(), ReLU(), ...) runs as one fused operation.
  • The next batch of pictures is decoded on the CPU while the GPU trains on the current one.

How the CUDA backend is fast

  • Convolutions are implicit GEMMs: one kernel reads the image straight from memory through a small per-shape table (no 9× im2col copy) and writes the result directly in NCHW (no transposes). 128 × 128 tiles, each thread holding an 8 × 8 block in registers, double-buffered shared memory read as conflict-free vectors.
  • The input gradient of a stride-1 convolution is the same kernel with the flipped, transposed weights; the weight gradient splits its long sum over the batch into segments that run in parallel and are added in a fixed order.
  • BatchNorm statistics are parallel reductions (fp32 within a thread, double across threads), and BatchNorm followed by an activation runs fused, recomputing instead of storing.
  • Workflow shares the GPU's primary context with the CUDA runtime, so it runs in the same process as PyTorch, CuPy or other CUDA libraries.

Speed against PyTorch

The same network (traced from Workflow and replayed op by op in PyTorch with the same weights), the same input, fp32, AdamW, one training step = forward + backward + optimizer step. Ratios above 1 mean Workflow is faster. benchmarks/vs_pytorch.py reproduces them; before timing it checks both against a float64 run (Workflow is as close to exact as PyTorch or closer).

On NVIDIA GPUs PyTorch is still faster. Part of that is cuDNN's Winograd convolutions for 3 × 3 kernels: they do fewer multiplications, at slightly lower precision (on the GTX 1050 they reach 3.0–3.4 "TFLOPS" on a card whose fp32 peak is 1.9). Workflow keeps every convolution an exact fp32 sum; its kernels run at 40–55% of that peak. Version 0.5 made CUDA training 2.3× faster than 0.4 (detector 320 px, batch 4: 34.5 → 80.7 images/s).

Correctness

Every operation and gradient is tested against PyTorch on the CPU (tests/test_core.py, PyTorch as a test oracle only), and every accelerator is tested against the CPU (tests/test_parity.py). On a GTX 1050 all 26 operations match the CPU core to 4e-7 relative error, and on Apple MLX to 6e-7.

Threads

The CPU core uses one thread per core, up to 16.
